# H100 SXM benchmark: JEV-27B-VL W4A8 on Decidra

Measured 2026-10-21 on a rented Vast.ai NVIDIA H100 SXM (Hopper, SM90), using a
CUDA 12.4 / SM90 build of the native engine. One resident server, exact decision
cache disabled, W4A8 checkpoint + LoRA adapter.

**Bottom line:** the engine runs on H100, but the current SM89-tuned kernels do
**not** exploit Hopper. H100 throughput is roughly **RTX 4090-class** (57 req/s
at saturation vs 56.6; 4.19K tok/s at 19.5K prefill vs ~3.94K), only **1.16×**
the L40S at short saturation and **1.39–1.44×** on long prefill, despite **4.3×**
the L40S's measured HBM bandwidth. Its real win is capacity: **122,516 tokens**
verified in 80 GB, versus 64K on the L40S and 32K on the 4090.

## Porting notes

The H100 is SM90; the shipped cubins are SM89 and cannot execute on it. The build
now takes `DECIDRA_CUDA_ARCH` (default `sm_89`) and names artifacts per
architecture. For this host the Rust `cudarc` feature must be `cuda-12040`
(driver 550.x), not the default `cuda-13000`; the remote build used a one-line
change in `native/Cargo.toml`:

```bash
DECIDRA_CUDA_ARCH=sm_90 DECIDRA_NVCC=/usr/local/cuda/bin/nvcc \
  cargo build --release --locked --features native
```

CUDA 12.2 (the attached $1.738/h offer, driver 535) **cannot compile the Marlin
kernel for SM90**: `ptxas` rejects the FP8 `mma.sync ... e4m3` instantiations even
though they are dead code for this checkpoint. CUDA 12.4 compiles them. The
adjacent driver-550 offer (`40179475`, same $1.7333/h) was used instead. On a
CUDA 13 driver, the normal `sm_90` build should work without the cudarc change.

## Short requests (~71 tokens)

Cold-client harness numbers (three runs, 16 requests/level):

| concurrency | H100 req/s | H100 p50 | L40S req/s | 4090 req/s |
|---:|---:|---:|---:|---:|
| 1 | 17.91 | 53.7 ms | 18.51 | 24.2 |
| 2 | 20.23 | 101.3 ms | 28.12 | 38.3 |
| 4 | 27.59 | 133.2 ms | 31.17 | 53.6 |
| 8 | 35.29 | 208.3 ms | 37.57 | 56.8 |
| 16 | 37.40 | 241.0 ms | 41.70 | 56.6 |

Warm persistent connections, 256 requests per level, and a 10 ms batch window:

| max_batch | c=16 | c=32 | c=64 | c=128 | c=256 |
|---:|---:|---:|---:|---:|---:|
| 8 | 50.6 | 50.2 | 50.0 | 49.7 | — |
| 32 | 46.2 | 50.9 | **55.1** | 53.9 | — |
| 64 | — | 51.6 | 56.1 | **57.3** | 56.3 |
| 8 (INT8 off) | 39.0 | 46.5 | 49.6 | 49.3 | — |

**Best short throughput: 57.3 req/s at c=128 with `MAX_BATCH=64`**, p50 2.09 s,
p95 2.22 s, mean batch 42.7. L40S peaked at 49.2 req/s with warm connections
(+16%); the 4090's cold-harness peak was 56.8 req/s. Larger than batch 64 adds
queueing without throughput. Disabling the per-token INT8 path is slower.

At c=2 the server formed batches of **1.0** even with a 10 ms window, so H100
low-concurrency requests serialize; c=4 averaged 2.7. The saturation script
removes client connection skew, but the server-side tokenize/enqueue path still
staggers pairs.

| 4,832 | 1.104 s | 4,368 | 3,617 | ~4,529 @4,090 |

| 19,498 | 4.658 s | 4,187 | 3,021 | ~3,939 @16,322 |

H100 is roughly **4090-class** (0.95–1.06× depending on length) and **1.2–1.4×
the L40S** in token throughput, not the 4× its bandwidth suggests. At long sequence lengths the run hits the
700 W cap (695 W at 122K) and 1,980 MHz, so it is compute/issue-bound.

## Maximum context

| prompt tokens | latency | tok/s | peak GPU memory |
|---:|---:|---:|---:|
| 65,767 | 17.79 s | 3,697 | 48.3 GB |
| 97,813 | 28.62 s | 3,417 | ~48 GB |
| **122,516** | **38.38 s** | **3,192** | **48.4 GB** |

A ~130K-token request (bench target 106,000) fails with
`CUDA_ERROR_ILLEGAL_ADDRESS` after ~10 s; targets 107,000/108,000 fail the same
way. A fresh server fails identically, so it is not pool reuse. Peak memory at
the failure is only ~50.7 GB of 80 GB, so this is **not OOM**. Disabling
FlashInfer attention or the chunked GDN path does not fix it. The verified
maximum is therefore **122,516 tokens**; the failure boundary lies between
122.5K and ~130K and is consistent with a 2^17 sequence/workspace index, but the
exact kernel has not been isolated. This is below the checkpoint's 262,144-token
model limit.

The engine's low-memory pool caps the 64K–122K working set at ~48 GB; the 80 GB
card has headroom that the current allocator does not use.

## Quality

28-row W4A8 suite against `eval/data/w4a8-cpu-suite28.json`:

| config | top-1 | mean KL | mean MAE | max Δ |
|---|---:|---:|---:|---:|
| H100 SM90 | 28/28 | **2.98e-4** | **3.485e-3** | 4.204e-2 (`r02`) |
| L40S SM89 grid 128 | 28/28 | 3.33e-4 | 3.486e-3 | 4.206e-2 |
| 4090 (README) | 28/28 | 2.33e-4 | 3.28e-3 | 1.76e-2 |

Top-1, KL, and MAE pass; the 0.02 max-delta gate fails on the same near-tie row
as L40S. H100's output is essentially the L40S grid-128 result, so the SM90
kernels are numerically consistent, not a new correctness regression.

## Why H100 is not faster

The engine's kernels are tuned for Ada/SM89 and use `mma.sync`/WMMA, not Hopper's
WGMMA/TMA. At batch 1 the H100 streams weights at only ~240 GB/s (7.6% of its
3.17 TB/s), and its 1.98 GHz clock is below the 4090's ~2.9 GHz; per-SM
`mma.sync` throughput is about 0.7× the 4090, with only 3% more SMs. That predicts
~0.72× at batch 1 (observed 0.74×). The same effect limits long prefill and
attention.

To actually use the H100:

1. **Marlin/W4A8 with WGMMA + TMA** (or a CUTLASS 3.x Hopper W4A8 GEMM). This is
   the largest lever: the current Marlin path leaves most of the tensor cores
   idle at short batch.
2. **FlashAttention-3** for the full-attention prefill layers; the vendored
   FlashInfer path is FA2.
3. **WGMMA GDN/prefill kernels**; the chunked GDN path is WMMA TF32.
4. **CUDA graphs** to cut launch overhead at low concurrency.
5. Fix the >122K sequence illegal-address bug before advertising the model's
   262K context.

None of these is a configuration change. Larger batches (64) and a 10 ms window
buy only ~13% over batch 8; disabling INT8 is a regression.

## Reproduce

```bash
# H100 build (remote copy; default Cargo feature is cuda-13000)
sed -i 's/cuda-13000/cuda-12040/' native/Cargo.toml
export DECIDRA_CUDA_ARCH=sm_90 DECIDRA_NVCC=/usr/local/cuda/bin/nvcc
cargo build --release --locked --features native

# server (same W4A8 env as docs/L40S.md)
export DECIDRA_CUDA_LIBS=/usr/local/cuda/lib64
export LD_LIBRARY_PATH=/usr/local/cuda/lib64:$LD_LIBRARY_PATH
# for saturation: MAX_BATCH=64, BATCH_WINDOW_US=10000

python3 eval/saturate.py --concurrency 16,32,64,128 --requests 256
python3 eval/bench.py --mode long --concurrency 1 --long-sizes 4090,9000,16383 \
  --long-requests 3 --chars-per-token 4.0 --warmup 3
python3 eval/suite.py --a-url http://127.0.0.1:8501 \
  --baseline eval/data/w4a8-cpu-suite28.json \
  --max-delta 0.02 --max-mae 0.004 --max-kl 0.001
```

Raw artifacts: `eval/out/h100/{h100_base,h100_sat8,h100_sat_win10,h100_sat_b32,h100_sat_b64,h100_int8off,longctx,one-*}/`.
