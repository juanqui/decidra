# L40S benchmark: JEV-27B-VL W4A8 on Decidra

Measured 2026-10-21 on a rented Vast.ai NVIDIA L40S (Ada, SM89), against the
RTX 4090 numbers published in the README. One resident Decidra server, exact
decision cache disabled, W4A8 checkpoint + LoRA adapter.

**Bottom line:** the L40S is **22–26% slower** than the RTX 4090 on this engine.
The engine is HBM-bandwidth-bound: the L40S measured **739 GB/s** of read
bandwidth against the 4090's 1,008 GB/s theoretical, and the long-context
throughput ratio is **0.77–0.81**, matching that bandwidth ratio. The L40S does
win on capacity: **64K-token prompts** fit in 48 GB (34.9 GB peak), versus the
4090's verified 32K limit.

## Method

- Same `eval/bench.py` harness and prompt generator as the 4090 baseline,
  seed 0, `DECIDRA_DECISION_CACHE_SIZE=0`.
- Short: 16 unique ~71-token prompts per level, concurrency 1/2/4/8/16, three
  runs, medians reported.
- Long: cold unique documents, concurrency 1, three requests per size, medians.
  Targets were chosen so the actual token counts match the 4090 probes:
  **4,090 / 8,151 / 16,322** vs the published **4,090 / 8,178 / 16,383**.
- Server config (best measured): `DECIDRA_NATIVE_GPU_EMBED=true`,
  `DECIDRA_NATIVE_INT8_EXCLUDE=none`, `DECIDRA_NATIVE_INT8_GROUP_SCALE=false`,
  `DECIDRA_NATIVE_MAX_BATCH=8`, window 2000 µs, max batch tokens 16384.
- 4090 numbers are the README W4A8 table. The local 4090s were occupied by
  other inference processes, so the benchmark was not rerun on them.

## Short requests (~71 tokens)

| concurrency | L40S req/s | 4090 req/s | ratio | L40S p50 | 4090 p50 | p50 ratio |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 18.82 | 24.2 | **0.78×** | 50.8 ms | 41.6 ms | 1.22× |
| 2 | 28.25 | 38.3 | **0.74×** | 66.0 ms | 52.4 ms | 1.26× |
| 4 | 29.26 | 53.6 | **0.55×** | 128.9 ms | 73.9 ms | 1.74× |
| 8 | 38.65 | 56.8 | **0.68×** | 201.7 ms | 122.6 ms | 1.65× |
| 16 | 41.89 | 56.6 | **0.74×** | 231.7 ms | 188.0 ms | 1.23× |

The c4/c8 gap is partly client-side. This harness creates new HTTP connections
inside the timed level; on the slower L40S host the four requests arrive in two
groups, so c4's mean batch size was **2.0** (4090: 4.0). With connections
pre-opened and synchronized, the same server reached:

| concurrency | warm-connection req/s | harness req/s |
|---:|---:|---:|
| 1 | 18.79 | 18.82 |
| 2 | 29.69 | 28.25 |
| 4 | 33.76 | 29.26 |
| 8 | 36.83 | 38.65 |
| 16 | **49.23** | 41.89 |

A 10 ms batch window raised c4 to 32.05 req/s and cut p50 to 107.8 ms, but did
not help c8/c16, so 2 ms remains the better default. `MAX_BATCH=16` gave no
throughput gain and raised c16 p50 to 315 ms; keep 8.

## Cold long prefill

| prompt tokens | L40S latency | L40S tok/s | 4090 latency | 4090 tok/s | ratio |
|---:|---:|---:|---:|---:|---:|
| 4,090 | 1.117 s | 3,655 | 0.903 s | 4,529 | **0.81×** |
| 8,151 | 2.330 s | 3,488 | 1.846 s | 4,430 | **0.79×** |
| 16,322 | 5.353 s | 3,047 | 4.159 s | 3,939 | **0.77×** |

All choices were correct; GPU utilization was 100%, temperature ≤65 °C, power
317 W median / 346 W max (cap 350 W), SM clock 2,348–2,400 MHz. The 4090 pulls
420–430 W at the same points, so the L40S is not thermally limited — it runs out
of memory bandwidth first.

## L40S-specific tuning

Measured on the same 4,832 / 10,705 / 19,498-token probes (baseline = host
embedding, Marlin grid 128):

| variant | 4.8K tok/s | 10.7K tok/s | 19.5K tok/s | long Δ | short Δ |
|---|---:|---:|---:|---:|---:|
| baseline (host embed, grid 128) | 3,464 | 3,284 | 2,889 | — | — |
| GPU embedding table | 3,534 | 3,348 | 2,942 | +1.9% | ~0 |
| SM-aware Marlin grid (142 blocks) | 3,617 | 3,425 | 3,021 | +2.7% | ~0 |
| both (shipped result) | — | — | — | **+4.4%** | ~0 |

The SM-aware grid is the only code change worth keeping. `native/src/version`
hard-coded Marlin to 128 persistent blocks, the RTX 4090's SM count; on a 142-SM
L40S that leaves 14 SMs unused. The kernel's split-K lock array was also sized
128; launching 142 blocks without growing it hung the first forward at 100%
utilization and ~100 W, so the two must change together. The patch:

- `Gpu` queries `CU_DEVICE_ATTRIBUTE_MULTIPROCESSOR_COUNT` into `Gpu::sms`.
- `marlin_gemm`, `marlin_gemm_int8`, and `marlin_gemm_fp8` launch `sms` blocks.
- `marlin_locks` is allocated with `max(sms, 128)` entries.

On a 4090 `sms = 128`, so the patch is behavior-identical there. On the L40S it
adds ~2.7% long-prefill throughput and slightly moves the numerics (still
top-1 identical). GPU embedding is worth enabling when the extra 2.4 GB fits.

## Quality

28-row W4A8 suite against `eval/data/w4a8-cpu-suite28.json`:

| config | top-1 | mean KL | mean MAE | max Δ | verdict |
|---|---:|---:|---:|---:|---|
| L40S, grid 128 | 28/28 | 3.33e-4 | 3.486e-3 | 4.206e-2 | KL/MAE pass, max Δ > 0.02 |
| L40S, grid 142 | 28/28 | **2.03e-4** | **2.666e-3** | 3.055e-2 | KL/MAE pass, max Δ > 0.02 |
| 4090 (README) | 28/28 | 2.33e-4 | 3.28e-3 | 1.76e-2 | pass |

The failed gate is one near-tie row (`r02`: L40S 0.519/0.481, golden
0.561/0.438); top-1 is unchanged. The L40S grid-142 result is closer to the CPU
golden than the published 4090 run on both KL and MAE. Treat the 0.02 max-delta
gate as not portable across SM counts for near-ties; do not treat this as a
top-1 regression. Exact probabilities were deterministic across runs.

## Capacity: 32K and 64K contexts

| prompt tokens | latency | tok/s | peak GPU memory |
|---:|---:|---:|---:|
| 33,216 | 11.69 s | 2,841 | 26.96 GB |
| 65,767 | 25.65 s | 2,564 | 34.90 GB |

Both completed with correct decisions. At 24,576 tokens the engine switches to
its low-memory buffer pool, so 32K uses less memory than the 19.5K probe
(26.96 GB vs 33.75 GB including GPU embedding). This is the L40S's practical
advantage over the 24 GB 4090, whose verified maximum is 32K.

## What would actually close the gap

1. **Memory bandwidth.** Nothing in the kernel schedule creates the missing
   230 GB/s. L40S throughput tracks measured HBM read bandwidth within a few
   percent at every long-context size.
2. **Clock/power.** The L40S runs 2.35–2.40 GHz at ~320 W; the 4090 runs
   ~2.91 GHz at 420–430 W. Attention and elementwise phases lose proportionally.
3. **Batching.** Warm connections recover most of the c4/c16 deficit; a
   production client that keeps connections open will see ~49 req/s at c16, not
   the harness's 42.
4. **More SMs only help compute-bound tails.** The 128→142 grid patch is worth
   keeping, but it buys 2.7%, not 25%.

## Reproduce

```bash
# server
export DECIDRA_CHECKPOINT=/workspace/models/jev-w4a8
export DECIDRA_NATIVE_MODEL=$DECIDRA_CHECKPOINT
export DECIDRA_TOKENIZER=$DECIDRA_CHECKPOINT/tokenizer.json
export DECIDRA_LORA_ADAPTER=$DECIDRA_CHECKPOINT/adapter_vllm
export DECIDRA_NATIVE_INT8_EXCLUDE=none
export DECIDRA_NATIVE_INT8_GROUP_SCALE=false
export DECIDRA_NATIVE_GPU_EMBED=true
export DECIDRA_DECISION_CACHE_SIZE=0
export DECIDRA_CUDA_LIBS=/usr/local/cuda/lib64
./target/release/decidra

# short sweep, 3 runs
python3 eval/bench.py --mode batch --batch-concurrency 1,2,4,8,16 \
  --batch-requests 16 --batch-tokens 69 --chars-per-token 3.38 --warmup 3
# long, matched to the 4090 probes
python3 eval/bench.py --mode long --concurrency 1 \
  --long-sizes 3462,6876,13766 --long-requests 3 --chars-per-token 4.0 --warmup 3
# quality
python3 eval/suite.py --a-url http://127.0.0.1:8501 \
  --baseline eval/data/w4a8-cpu-suite28.json \
  --max-delta 0.02 --max-mae 0.004 --max-kl 0.001
```

Raw artifacts (batch JSON, suite JSON, GPU telemetry) are in
`eval/out/l40s/{baseline,gpuembed,win10,sm142,longmatch,ctx32k,ctx64k}/`.
